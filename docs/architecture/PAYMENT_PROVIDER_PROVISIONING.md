# School Payment Provider Provisioning

## Trust boundaries

CIPA coordinates this job only after PIAM has approved the provider operation.
The job runtime is `payment-provider-provisioner-runtime`; infrastructure
deployment remains the responsibility of `infrastructure-deployer`. The
Cloud Run Job specification is
`deploy/cloud-run/curriculum-payment-provider-provisioner-job.yaml`.

The shared `SchoolPaymentProviderProvisioningContract` binds a request to one
tenant, school, provider, operation, PIAM approval, and tenant-specific Secret
Manager credential version. The job verifies a CIPA HMAC over the serialized
contract before reading credentials. Raw credentials must not be put in the
contract, environment variables, logs, database operation records, or
`curriculum-billing-payments` requests.

The provisioning service requires a provider adapter to return actual
provider-response references, merchant/account references, settlement
verification, webhook registration and signature evidence, verified
capabilities, provider health, and account status. Missing adapters,
incomplete evidence, cross-tenant secret references, unsigned contracts, and
missing PIAM approval fail closed. Provider references are accepted as
evidence only when the adapter verifies them against provider responses; they
must never be generated by this job.

The billing-payments synchronization payload contains only provider-account
metadata and the Secret Manager version resource name. This operation does not
create or verify payments. Checkout processing, inbound webhook signature
verification, payment status, and settlement reconciliation remain owned by
`curriculum-billing-payments`.

## Provider adapter and integration status

The orchestration, contract validation, tenant-scoped Secret Manager access,
authenticated billing client, and adapter interface are implemented in
`server/paymentProviderProvisioning.ts`. The five provider choices are
Paystack, Flutterwave, OPay, Interswitch, and approved bank-transfer providers.
The CIPA dispatch/signing path and the production job image entrypoint are not
wired in this repository yet; the Cloud Run YAML is a deployment specification,
not a ready-to-deploy image.

Live provider connectors are **not configured**. Merchant registration and
linking APIs, required KYC/PIAM evidence, settlement verification, webhook
registration/signature semantics, and supported capabilities must be
implemented and reviewed against each provider's current merchant agreement
and official API. In particular, bank transfer is not a single provider API.
Until an adapter exists and is independently validated, the job rejects that
provider with `PROVIDER_ADAPTER_UNAVAILABLE`; this is intentional and is not a
successful provisioning result.

The dedicated `curriculum-billing-payments` service is in this repository,
but its provider-account synchronization endpoint is not implemented. The client currently targets
`POST /internal/v1/payment-provider-accounts`; the receiving service must
implement and authorize this contract, enforce the operation idempotency key,
and reject payment-success fields before this integration can be enabled.

The existing `serverPaymentEngine.ts` contains synthetic payment profiles,
credentials, virtual accounts, and checkout URLs. This new provisioner does
not call those methods. They must not be used as evidence or as a source of
production provider configuration.

## Billing service safety status

Payment initialization and refunds are disabled in code, including when
`BILLING_PAYMENTS_ENABLED=true`; enabling them requires implementation review
and provider-specific sandbox and financial acceptance evidence. The service
verifies Paystack and Flutterwave callbacks against their provider APIs before
posting, but these paths have not been certified with sandbox transactions.
OPay, Interswitch and bank-transfer verification and settlement are not
enabled. Provider API mocks are not sandbox evidence.

`/healthz` reports process liveness. `/readyz` checks database connectivity,
the required billing tables' forced RLS, basic runtime-role restrictions and
the database signing-key configuration. It does not certify migration
checksums, effective privileges, provider integrations, or financial readiness.
Cloud Run IAM must restrict invocation to the backend runtime; the application
does not independently validate Cloud Run identity tokens.

Before deployment, provision and verify a dedicated restricted database role
and Secret Manager connection secret, review the shared control-plane signing
key trust boundary, build a dedicated service image, configure network access,
and verify Cloud Run IAM, monitoring and readiness in the target project. The
deployment script alone does not establish those prerequisites.

## Secret Manager lifecycle

Credential intake is a tenant-specific secret version named
`projects/PROJECT_ID/secrets/curriculum-payment-intake-TENANT_UUID-PROVIDER/versions/VERSION`.
The job verifies the tenant and provider encoded in the resource name, reads
the payload only after validating the signed contract, and writes the
credential bundle to a tenant- and provider-specific destination secret:

`projects/PROJECT_ID/secrets/curriculum-payment-TENANT_UUID-PROVIDER-HASH`

Destination secrets must be created by an authorized provisioning workflow
before the job runs. The job does not create secrets, invent credentials, or
derive a merchant ID or account number. Secret Manager versions provide
encryption at rest; configure CMEK on the secret when required by policy.
Rotation creates a new version only after the provider confirms the rotated
credential and the adapter verifies the account. Retain the previous version
for an approved rollback window; disable/destroy it only through the approved
credential lifecycle process.

Provider operations must use the contract idempotency key with provider APIs.
Secret Manager version creation and the billing-payments synchronization
must also be made idempotent before enabling automatic Cloud Run retries.

## Job deployment and IAM preparation

Substitute `PROJECT_ID`, `REGION`, `IMAGE_TAG`, and the billing service URL in
the YAML before deployment. The runtime account must remain distinct from
`infrastructure-deployer`. Do not apply IAM changes as part of this
implementation.

Candidate least-privilege bindings, subject to live inventory and approval:

| Principal | Resource scope | Candidate permission |
| --- | --- | --- |
| CIPA caller | This Cloud Run Job only | `run.jobs.run` (a job-scoped role containing this permission) |
| `payment-provider-provisioner-runtime` | Exact per-tenant intake secrets | `secretmanager.versions.access` |
| `payment-provider-provisioner-runtime` | Exact per-tenant destination secrets | `secretmanager.versions.add` |
| `payment-provider-provisioner-runtime` | `curriculum-billing-payments` Cloud Run service only | `run.routes.invoke` (typically `roles/run.invoker`) |
| CIPA and provisioner | Exact contract-signing secret only | Secret access needed to sign/verify the CIPA handoff |

These are candidates, not confirmation of current identities, deployed
resources, or effective grants. Pre-create destination secrets and apply
Secret Manager grants at individual secret scope; do not grant project-wide
secret access. Keep PIAM approval, account creation, and human-controlled
merchant actions in the authoritative PIAM workflow.

## Acceptance and rollout gate

The tests in `server/paymentProviderProvisioning.test.ts` cover signature
rejection, tenant isolation, missing-adapter fail-closed behavior,
tenant-specific secret naming, and Secret Manager request encoding through a
test transport. They do not simulate provider success or exercise a live GCP
project.

Before deploying the job or enabling CIPA dispatch, implement and validate a
real provider adapter for each enabled provider, provision dedicated
provider-approved test accounts, add provider contract tests that use
official sandbox APIs, configure and test Secret Manager access, deploy and
authorize the billing-payments endpoint, and perform retry/rotation/
suspension/revocation tests. No production IAM changes or live merchant
operations are performed by this repository change.
